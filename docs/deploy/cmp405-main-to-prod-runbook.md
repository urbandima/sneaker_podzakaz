# Runbook: первая реальная выкатка main → прод

Готовится по [CMP-405](../../CMP/issues/CMP-405). Deploy-production job в
`.github/workflows/ci.yml` ни разу не запускался — прод всё ещё на версии
до всех изменений, перечисленных ниже. Это первый реальный деплой этого
приложения через CI, а не рутинный релиз.

**Статус блокеров деплоя на момент написания:**
- `deploy-production` заблокирован отсутствующим SSH pubkey у совета — вне
  моего контроля, см. [CMP-379](../../CMP/issues/CMP-379).
- `test` (шаг «Run database migrations») — **починен и проверен** (CMP-405).
- `lint` (phpcs + phpstan) и `build` (gulp) — **всё ещё красные**, это два
  новых самостоятельных блокера, заведены отдельными issues (см. ниже).
  Их нужно закрыть до того, как `deploy-production` реально сможет
  запуститься, потому что `test`/`build`/`security` требуют `needs: lint`,
  а `deploy-production` требует `needs: [test, build, security]`.

Не относитесь к этому runbook как к «можно нажимать хоть сегодня» — сначала
должны закрыться оба новых блокера и появиться pubkey.

## 1. Оценка разрыва main ↔ прод (read-only)

- **Коммитов в main:** 575 всего в истории репозитория; deploy-production
  ни разу не выполнялся, поэтому весь набор — потенциальный дифф для прода.
- **Значимые изменения, которые уедут одним деплоем:**
  - смена рантайма PHP 7.4 → PHP 8.4 (`composer.json` требует `>=8.1.0`,
    локально проверено на 8.4.13);
  - nginx micro-cache (`config/nginx/default.conf`, `X-Cache` заголовок) —
    **требует контроля над конфигом nginx на хосте**; на shared-хостинге
    вроде `vh124.hoster.by` это не всегда доступно клиенту напрямую —
    проверить на месте, не предполагать;
  - фикс `/catalog` 500 (`518b834`);
  - рефакторинг AmoCRM Week 1–3 (CMP-371);
  - удаление legacy `zakaz` (CMP-389);
  - `OrderShippingService` (`50cb460`);
  - весь набор миграционных фиксов из этого issue (CMP-405).
- **Отдельным решением совета, но в то же окно:** ротация
  `COOKIE_VALIDATION_KEY` + `auth_key` из
  [CMP-401](../../CMP/issues/CMP-401) — процедура уже готова в
  [docs/security/cmp-401-cookie-rotation-runbook.md](../security/cmp-401-cookie-rotation-runbook.md),
  запускается только после отдельного решения совета по CMP-352 п.6.
  Не автоматизировать, не запускать заодно с этим деплоем без явного «да».

### Миграции на боевой базе

- Миграций в репозитории: **154**. Прод ни разу не проходил через
  `php yii migrate` в рамках CI — значит на первом реальном деплое
  применится либо весь набор (если прод-БД вообще без миграционной
  истории), либо неизвестный остаток (если кто-то раньше накатывал
  миграции вручную мимо CI). **Это первое, что нужно проверить на месте**
  read-only командой (см. шаг 2 ниже) — до `migrate up`.
- Явно помеченных как «не откатывается» / «no rollback» — минимум 8
  (`m251102_081314_add_brand_seo_fields`,
  `m251102_104112_add_vendor_code_to_product`,
  `m251106_134103_add_model_name_to_product`,
  `m251108_172031_add_missing_order_fields`,
  `m251226_130000_ensure_tariff_table`,
  `m260330_091448_add_test_data_simple`,
  `m260331_085833_add_is_active_to_coupon_table`,
  `m260426_200500_fix_supplier_country`). По существу они безопасны (add
  column / условные фиксы), но откат = только restore из бэкапа.
- Миграции, реструктурирующие данные (не просто DDL) — например
  `m260427_100000_migrate_orders_to_three_tracks` — тоже фактически
  необратимы «по кнопке»: `safeDown()` не восстанавливает предыдущую
  раскладку статусов автоматически. Откат = restore из бэкапа БД.
- Демо/тестовые сид-миграции (`m260318_100000_create_demo_customers`,
  `m260325_064616_add_test_orders`) теперь **гарантированно** не создают
  данные на `YII_ENV_PROD` — проверено в этом issue.

### Требования к PHP на хостинге

- `composer.json`: `"php": ">=8.1.0"`.
- `ci.yml` тестирует и деплоит на PHP 8.1.
- Локально код совместим и с PHP 8.4.13 (полный прогон миграций +
  phpunit зелёный).
- **Открытый вопрос:** какая версия PHP реально включена на
  `vh124.hoster.by`. По условиям задачи — не заходить в панель, не
  использовать утёкший пароль cPanel. Единственный безопасный способ
  узнать — после получения SSH-доступа выполнить `php -v` на сервере
  (read-only), это первый шаг runbook'а ниже, до каких-либо изменений.
  Если сервер даёт только PHP 7.4/8.0 — деплой этой версии кода
  невозможен без смены PHP-версии в cPanel (MultiPHP Manager) сначала.

## 2. Порядок выкатки (когда появится pubkey и закроются lint/build)

Выполнять строго по шагам, каждый — с подтверждением перед следующим.

### 2.1. До деплоя (read-only, безопасно повторять)

1. `ssh <user>@vh124.hoster.by` — проверить доступ.
2. `php -v` — сверить с требованием `>=8.1.0`.
3. `cd <DEPLOY_PATH> && git log -1 --format='%H %ci'` — зафиксировать,
   на каком коммите сейчас живёт прод (это и есть точка возможного отката).
4. `php yii migrate/history` (или прямой `SELECT * FROM migration ORDER BY apply_time`)
   — какие миграции прод уже считает применёнными. **Не запускать `migrate up`,
   пока не сверили этот список** — если он расходится с ожиданием
   (например, кто-то накатывал миграции вручную), сначала разобраться,
   не гадать.
5. Бэкап БД: `mysqldump` полной базы (не только `user`/`customer` — в
   отличие от точечного бэкапа для CMP-401, здесь меняется схема
   полностью, нужен full dump с возможностью restore).
6. Бэкап файлов (текущий код + `.env`) — `tar` в отдельную директорию
   вне репозитория, не поверх рабочей копии.

### 2.2. Сама выкатка

7. `git fetch && git log HEAD..origin/main --oneline` — финальная сверка
   диффа перед `pull`.
8. `git pull origin main`.
9. `composer install --no-dev --optimize-autoloader`.
10. `npm ci && npm run build` (если `build`-job CMP-40Y к этому моменту
    уже зелёный локально — сверить, что тот же результат воспроизводится
    и на сервере).
11. `php yii migrate --interactive=0` — теперь можно, после шага 2.1.4.
    Если упадёт на середине — **не паниковать и не откатывать вручную**:
    Yii2 миграции внутри одного файла идут в транзакции (`safeUp`), но
    между файлами — нет. Смотреть, какая миграция упала, сверять с
    списком «no rollback» выше, при необходимости — restore из бэкапа
    шага 2.1.5 целиком (частичный откат риskovanнее полного restore).
12. `php yii cache/flush-all`.
13. Перезапуск PHP-FPM/OPcache — способ зависит от того, что реально
    доступно на shared-хостинге (через cPanel или `touch` на
    `.htaccess`/passenger restart-файл — уточнить на месте, не
    предполагать systemctl, как ошибочно указано в
    `scripts/deploy-production.sh`, см. примечание ниже).

### 2.3. Сброс сессий (если решено ротировать ключи в это же окно)

Если в это же окно утверждена ротация `COOKIE_VALIDATION_KEY`/`auth_key`
по CMP-401 — выполнять **после** шага 12, по отдельному runbook'у
[cmp-401-cookie-rotation-runbook.md](../security/cmp-401-cookie-rotation-runbook.md).
Она разлогинивает сотрудников админки, но НЕ покупателей (разные
механизмы авторизации) — если нужно разлогинить и покупателей, это
отдельное явное решение, не побочный эффект.

## 3. Smoke-checks после выкатки

Минимум, по порядку:

1. `curl -sI https://sneaker-head.by/` → `200`.
2. `curl -sI https://sneaker-head.by/catalog` → `200` (сейчас `500` —
   это главный сигнал успеха: `518b834` действительно доехал и БД в
   рабочем состоянии).
3. Повторный запрос `/catalog` → заголовок `X-Cache: HIT` (проверяет,
   что micro-cache реально работает на этом хостинге, а не просто
   присутствует в конфиге).
4. Залогиниться в админку тестовым/боевым аккаунтом, открыть один
   существующий заказ — проверяет, что `order`/`order_history`/
   `order_item` пережили миграции без потери данных.
5. Оформить один тестовый заказ на витрине до шага оплаты (не
   подтверждать реальную оплату) — проверяет `OrderShippingService`
   (CMP-392) и checkout end-to-end.
6. `php yii queue/info` или эквивалент, если в проекте есть очереди —
   проверить, что воркеры подхватили новый код (иначе будут молча
   работать на старой версии до перezапуска).

Если шаг 2 (`/catalog` → 200) не проходит — это блокирующий фейл,
переходить к откату (раздел 4), не разбираться на живую.

## 4. План отката

Приоритет: **скорость возврата в рабочее состояние**, не сохранение
данных, накопленных за минуты простоя (их и не будет — сайт был в 500
до деплоя).

1. Код: `git checkout <SHA из шага 2.1.3>` (или restore файлового бэкапа
   шага 2.1.6) → `composer install --no-dev` под старым `composer.lock`.
2. БД: если миграции гарантированно не менялись между бэкапом и
   откатом — можно попробовать точечный `migrate down` для миграций,
   применённых в этом окне (сверить со списком «no rollback» — если
   среди применённых есть хоть одна оттуда, **не пытаться `migrate down`
   частично**, сразу full restore).
3. Full restore БД из дампа шага 2.1.5 — безопасный дефолт, если
   пункт 2 не гарантирован.
4. Сброс OPcache/кэша, перезапуск PHP-FPM тем же способом, что в шаге 2.2.13.
5. Повторить smoke-checks раздела 3 против откаченной версии.
6. Сообщить совету и в этот issue результат — откат тоже требует
   комментария с причиной.

## Примечание про существующие доки

`docs/PRODUCTION_DEPLOYMENT_GUIDE.md` и `scripts/deploy-production.sh`
описывают инфраструктуру, которой, по всей видимости, не существует на
реальном таргете (Docker Compose с Elasticsearch/Redis, `systemctl
php8.1-fpm`, путь `/var/www/sneakerhead` вместо `/var/www/sneaker-head`
из `ci.yml`, пользователь `www-data`). Это похоже на аспирационный
черновик под гипотетический VPS, а не под реальный shared-хостинг
`vh124.hoster.by`. Этот runbook его не использует и не предполагает —
считать `docs/PRODUCTION_DEPLOYMENT_GUIDE.md`/`scripts/deploy-production.sh`
устаревшими до отдельной проверки на месте.
