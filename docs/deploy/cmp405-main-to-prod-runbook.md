# Runbook: первая реальная выкатка main → прод

Готовится по [CMP-405](../../CMP/issues/CMP-405). Deploy-production job в
`.github/workflows/ci.yml` ни разу не запускался — прод всё ещё на версии
до всех изменений, перечисленных ниже. Это первый реальный деплой этого
приложения через CI, а не рутинный релиз.

**Статус блокеров деплоя на момент написания:**
- `deploy-production` заблокирован отсутствующим SSH pubkey у совета — вне
  моего контроля, см. [CMP-379](../../CMP/issues/CMP-379).
- `test` (шаг «Run database migrations») — **починен и проверен** (CMP-405).
- `lint` (phpcs + phpstan) и `build` (gulp) — **всё ещё красные**, это два
  новых самостоятельных блокера, заведены отдельными issues (см. ниже).
  Их нужно закрыть до того, как `deploy-production` реально сможет
  запуститься, потому что `test`/`build`/`security` требуют `needs: lint`,
  а `deploy-production` требует `needs: [test, build, security]`.

Не относитесь к этому runbook как к «можно нажимать хоть сегодня» — сначала
должны закрыться оба новых блокера и появиться pubkey.

## 1. Оценка разрыва main ↔ прод (read-only)

- **Коммитов в main:** 575 всего в истории репозитория; deploy-production
  ни разу не выполнялся, поэтому весь набор — потенциальный дифф для прода.
- **Значимые изменения, которые уедут одним деплоем:**
  - смена рантайма PHP 7.4 → PHP 8.4 (`composer.json` требует `>=8.1.0`,
    локально проверено на 8.4.13);
  - nginx micro-cache (`config/nginx/default.conf`, `X-Cache` заголовок) —
    **требует контроля над конфигом nginx на хосте**; на shared-хостинге
    вроде `<PROD_HOST>` это не всегда доступно клиенту напрямую —
    проверить на месте, не предполагать;
  - фикс `/catalog` 500 (`518b834`);
  - рефакторинг AmoCRM Week 1–3 (CMP-371);
  - удаление legacy `zakaz` (CMP-389);
  - `OrderShippingService` (`50cb460`);
  - весь набор миграционных фиксов из этого issue (CMP-405).
- **Отдельным решением совета, но в то же окно:** ротация
  `COOKIE_VALIDATION_KEY` + `auth_key` из
  [CMP-401](../../CMP/issues/CMP-401) — процедура уже готова в
  [docs/security/cmp-401-cookie-rotation-runbook.md](../security/cmp-401-cookie-rotation-runbook.md),
  запускается только после отдельного решения совета по CMP-352 п.6.
  Не автоматизировать, не запускать заодно с этим деплоем без явного «да».

### Миграции на боевой базе

- Миграций в репозитории: **154**. Прод ни разу не проходил через
  `php yii migrate` в рамках CI — значит на первом реальном деплое
  применится либо весь набор (если прод-БД вообще без миграционной
  истории), либо неизвестный остаток (если кто-то раньше накатывал
  миграции вручную мимо CI). **Это первое, что нужно проверить на месте**
  read-only командой (см. шаг 2 ниже) — до `migrate up`.
- Явно помеченных как «не откатывается» / «no rollback» — минимум 8
  (`m251102_081314_add_brand_seo_fields`,
  `m251102_104112_add_vendor_code_to_product`,
  `m251106_134103_add_model_name_to_product`,
  `m251108_172031_add_missing_order_fields`,
  `m251226_130000_ensure_tariff_table`,
  `m260330_091448_add_test_data_simple`,
  `m260331_085833_add_is_active_to_coupon_table`,
  `m260426_200500_fix_supplier_country`). По существу они безопасны (add
  column / условные фиксы), но откат = только restore из бэкапа.
- Миграции, реструктурирующие данные (не просто DDL) — например
  `m260427_100000_migrate_orders_to_three_tracks` — тоже фактически
  необратимы «по кнопке»: `safeDown()` не восстанавливает предыдущую
  раскладку статусов автоматически. Откат = restore из бэкапа БД.
- Демо/тестовые сид-миграции (`m260318_100000_create_demo_customers`,
  `m260325_064616_add_test_orders`) теперь **гарантированно** не создают
  данные на `YII_ENV_PROD` — проверено в этом issue.

### CMP-412: симуляция апгрейда с данными и рантайм-патчером — вердикт

Прод ни разу не проходил через `deploy-production`, поэтому его точное
миграционное состояние неизвестно и не восстанавливается однозначно (см.
выше). Вместо гадания прогнан воспроизводимый скрипт
[`scripts/simulate-prod-upgrade.sh`](../../scripts/simulate-prod-upgrade.sh)
на двух правдоподобных базовых точках — конец мая 2026 (миграции по
`m260513_100000_add_fulltext_index_to_product`, close к моменту последнего
известного изменения прод-кода — см. корреляцию с `/catalog` 500 в
[CMP-285](../../CMP/issues/CMP-285)) и конец 2025 (сразу после
архитектурного рефакторинга, `m251228_000000_create_tariff_calculation_history`)
— в обоих случаях: чекаут базовой точки → наполнение БД правдоподобным
объёмом данных (клиенты/товары/заказы/позиции заказа/купоны/категории с
вложенным множеством) → симуляция рантайм-патчера
`TariffSetupService::ensureOrderSupport()` (единственное место в
запрос-обслуживающем коде, которое меняет схему в рантайме — грепом
проверено, что других таких мест в `backend/`/`frontend/` нет; два
one-off скрипта `scripts/import_from_moysklad.php` и
`scripts/verify_ms_import.php` тоже правят схему, но не вызываются веб-
запросами, только вручную) → `migrate/up` до HEAD → проверка данных →
`migrate/to` обратно к базовой точке.

**Вердикт: апгрейд прод-базы безопасен при условии предварительного
full-backup БД (раздел 2.1.5) — фатальных падений `migrate/up` не найдено
ни на одном из двух сценариев, включая сценарий с рантайм-патчером.**

Детали:

1. **Гипотеза "Duplicate column" из-за `ensureOrderSupport()` —
   опровергнута.** Все три миграции, которые трогают те же колонки
   `order` (`tariff_id`, `commission_amount`, `delivery_cost`,
   `insurance_amount`, `tariff_weight_kg`) — `m251222_000001_admin_improvements`,
   `m251226_130000_ensure_tariff_table`, `m260921_140000_add_missing_purchase_tariff_columns_to_order`
   — уже защищены проверкой `if (!in_array(...))` / `isset($schema->columns[...])`
   до `addColumn`. На обеих базовых точках, с предварительно наложенным
   рантайм-патчером, `migrate/up` прошёл 100% миграций без единого
   падения.
2. **Сохранность данных подтверждена.** После полного `migrate/up`
   поверх наполненной БД: заказы/клиенты/товары/купоны/категории на
   месте, `coupon.name` (NOT NULL без дефолта) и `category.lft`/`rgt`
   (NOT NULL без дефолта, добавлено в CMP-410) не потеряли значения ни у
   одной существующей строки.
3. **Найдены и исправлены два реальных бага отката** (не гипотетических —
   воспроизведены и на симуляции с данными, и на чистой БД):
   - `m260704_210000_add_moysklad_fields_to_product_and_product_size.php`:
     `safeDown()` безусловно дропал колонку `product.vat`, которую эта
     миграция не создавала (владелец — более ранняя
     `m251105_105000_comprehensive_database_fix`) — откат стирал бы НДС
     у существующих товаров. Исправлено: колонка убрана из списка,
     которым управляет эта миграция.
   - `m260427_300000_create_missing_finance_feedback_tables.php`:
     `safeDown()` вызывал несуществующий метод `dropTableIfExists()` —
     откат **гарантированно падал на любой базе**, независимо от
     состояния данных. Исправлено на `getTableSchema()`-проверку +
     `dropTable()`, по образцу остальных миграций в репозитории.
   - `m260424_120000_add_field_change_to_order_history.php`:
     `safeDown()` безусловно дропал индекс, которым также управляет более
     поздняя `m260503_120000_add_product_fields_to_order_item` — при
     последовательном откате обеих миграций второй `dropIndex` падал на
     "index doesn't exist". Исправлено проверкой существования перед
     дропом.
4. **Обратимость ограничена по конструкции, не только из-за находок
   выше.** Полный `migrate/down` от HEAD на чистой БД останавливается
   через 63 из 158 миграций на `m260412_170000_fix_sidebar_menu_table`,
   которая **осознанно** объявляет себя необратимой (`safeDown()` явно
   возвращает `false`, комментарий "не удаляем колонки для безопасности").
   Это не баг — но означает, что `migrate down` в принципе не годится как
   план отката дальше нескольких последних миграций. **Единственный
   рабочий план отката — full restore из бэкапа шага 2.1.5**, как и было
   написано в разделе 4 изначально; эта симуляция лишь подтверждает, что
   альтернативы (точечный `migrate down`) не существует технически, а не
   просто не рекомендуется.
5. ~~Не проверено в этой итерации~~ — оба пункта закрыты в
   [CMP-415](../../CMP/issues/CMP-415), см. раздел ниже.

Как повторить: `scripts/simulate-prod-upgrade.sh <имя-последней-миграции-в-базовой-точке> [имя_бд]`.
Требует локальный MySQL (root без пароля) и `composer install` в текущем
чекауте. Скрипт ничего не пишет в `.env` репозитория и не трогает прод.

### CMP-415: сценарий «до-рефакторинговый/никогда не мигрированный прод» + живой HTTP-чекаут — вердикт

Закрывает оба пункта, оставленных открытыми в CMP-412 (раздел выше, было
«Не проверено в этой итерации»).

#### 1. До-рефакторинговая схема — `migrate up` **применим**, но с оговоркой про `customer`

Коммит `46b6c4137` («Глобальное изменение архитектуры и кода всего сайта»,
2026-03-16, 1280 файлов) переписал структуру каталогов, но **не сменил
систему миграций так, как можно было предположить**. Ключевой факт,
установленный сверкой файлов: из 57 файлов старой `migrations/` 56 были
перенесены в `infrastructure/migrations/` **под теми же именами версий**
(`m241023_181500_create_users_table`, `m251105_105000_comprehensive_database_fix`
и т.д. — идентификатор версии не менялся, только путь). Таблица истории
миграций Yii2 (`migration`) отслеживает применённые миграции по имени
версии, а не по пути к файлу — значит, если прод когда-либо прогнал
старые миграции (любым способом, включая ручной запуск `php yii migrate`
до рефакторинга), история миграций и так уже содержит эти 56 имён, и
`migrate up` с текущего HEAD корректно распознает их как применённые и
накатит только оставшиеся ~102 миграции, появившиеся уже после рефакторинга.

**Проверено эмпирически**, не только по чтению кода: старый чекаут
(`46b6c4137~1`) поднят в отдельном git worktree, его собственные миграции
прогнаны на чистой БД `migrate/up` до конца (56/56 применено), затем на
**той же БД** прогнан `php yii migrate/up` из текущего HEAD (без сброса) —
применилось 102 новые миграции, **`Migrated up successfully`, ни одного
фатального падения**. Данные (10 товаров, 8 брендов, 4 категории, 3
пользователя), заведённые ещё на старой схеме, пережили переход без потерь;
`coupon.name`/`category.lft`/`rgt` (NOT NULL без дефолта, CMP-410) —
без пустых значений, как и в сценариях A/B из CMP-412.

Побочный эффект той же проверки — **найдены и исправлены два
самостоятельных бага миграционного порядка**, существовавшие ещё в
дорефакторинговом коде (не внесены рефакторингом, тот их случайно
пофиксил при переносе):
- `m250102_000006_insert_test_products.php` (старая версия) вставлял
  тестовые товары с колонками `material`/`season`/`gender`/... — эти
  колонки появляются только в `m251105_091600_add_filter_fields_to_product`,
  на **11 месяцев позже** в порядке миграций. Чистый `migrate/up` от
  пустой БД на любой версии кода до рефакторинга падал на этой миграции.
- `m250102_120000_add_catalog_indexes.php` / `m250107_002700_add_performance_indexes.php`
  (старые версии) создавали индексы на колонках `rating`/`material`/
  `season`/`gender`/`eu_size`, которых на этом шаге миграционной цепочки
  ещё не существует — тоже падение на чистой БД.

Оба бага уже отсутствуют в текущих версиях этих файлов в
`infrastructure/migrations/` (рефакторинг 2026-03-16 случайно переписал
эти миграции в идемпотентном виде — `try/catch` вокруг `createIndex`,
урезанный список колонок в INSERT). Отдельного фикса в этом issue не
требовалось — только подтверждение, что зафиксированное в коде поведение
уже правильное. Важное следствие: **`migrate up` от полностью пустой БД
не проходил чисто ни на одной версии этого репозитория до сегодняшнего
дня**, ни до, ни сразу после рефакторинга — то есть гипотеза «прод вообще
никогда не имел никакой примененной миграционной истории» технически не
могла привести к рабочему сайту через `migrate up`; какая-то миграционная
история (пусть даже ручная, мимо CI) на проде обязана существовать, раз
сайт годами обслуживает трафик.

**Единственный найденный содержательный пробел** — таблица `customer`
целиком отсутствует в дорефакторинговой схеме (аккаунты велись через
таблицу `user`). Создание `customer` — одна из ~102 новых миграций,
`migrate up` создаст её пустой. Если реальный прод в этом сценарии,
переход **не переносит существующих покупателей** из `user` в `customer`
автоматически — это отдельный ручной шаг данных (data backfill), не
покрываемый `migrate up`, и его нужно спланировать отдельно **только
если** окажется, что прод действительно на дорефакторинговой схеме
(шаг 2.1.4 read-only проверки истории миграций покажет это сразу — если
среди применённых версий нет ни одной с именем из ~102 новых, это она).

**Вердикт: `migrate up` — применимое и достаточное понятие для схемы в
этом сценарии** (не «фактически повторная миграция данных с нуля», как
предполагалось в постановке задачи), при условии full-backup БД (как и во
всех остальных сценариях) и отдельного ручного шага для `user` → `customer`
backfill, если он потребуется по факту.

#### 2. Живой HTTP-чекаут поверх апгрейженной БД — пройден

Пересобран сценарий B из CMP-412 (`scripts/simulate-prod-upgrade.sh
m251228_000000_create_tariff_calculation_history cmp412_b`), поднят
`php -S 127.0.0.1:8765 -t frontend/web router.php` поверх `cmp412_b`,
через Playwright: добавление товара в корзину (`/cart/add`) → `/checkout`
→ заполнение полей, выбор доставки/оплаты (скрытые радио выставлены через
JS, как обычно на этом чекауте) → `submitOrder()` → `POST /order/create`.
**Результат: `200`, `{"success":true,"order_id":4,...}`, заказ реально
записан в `order` (проверено прямым SELECT), консоль браузера чистая, ни
одного HTTP 5xx за весь прогон.** `Order::rules()`/валидация не падают на
данных, прошедших полный апгрейд миграций.

По пути найден и исправлен независимый баг в
`scripts/simulate-prod-upgrade-seed-extra.sql`: INSERT в `order_item`
ссылался на колонку `product_id`, которая появляется только в
`m260503_120000_add_product_fields_to_order_item` (май 2026) — на
сценарии B (база = конец 2025) INSERT падал с "Unknown column", несмотря
на заявленный в комментарии файла инвариант «только гарантированно-
древние колонки». Убрано из INSERT; сценарий A (база = май 2026,
`product_id` уже существует) багом не затронут.

Как повторить: `scripts/simulate-prod-upgrade.sh
m251228_000000_create_tariff_calculation_history cmp412_b`, затем
временно указать в `.env` (не коммитить) `DB_DSN`/`DB_NAME` на `cmp412_b`,
поднять `php -S 127.0.0.1:8765 -t frontend/web router.php`, пройти
чекаут через браузер или Playwright на `/checkout`.

### Требования к PHP на хостинге

- `composer.json`: `"php": ">=8.1.0"`.
- `ci.yml` тестирует и деплоит на PHP 8.1.
- Локально код совместим и с PHP 8.4.13 (полный прогон миграций +
  phpunit зелёный).
- **Открытый вопрос:** какая версия PHP реально включена на
  `<PROD_HOST>`. По условиям задачи — не заходить в панель, не
  использовать утёкший пароль cPanel. Единственный безопасный способ
  узнать — после получения SSH-доступа выполнить `php -v` на сервере
  (read-only), это первый шаг runbook'а ниже, до каких-либо изменений.
  Если сервер даёт только PHP 7.4/8.0 — деплой этой версии кода
  невозможен без смены PHP-версии в cPanel (MultiPHP Manager) сначала.

## 2. Порядок выкатки (когда появится pubkey и закроются lint/build)

Выполнять строго по шагам, каждый — с подтверждением перед следующим.

### 2.1. До деплоя (read-only, безопасно повторять)

1. `ssh <user>@<PROD_HOST>` — проверить доступ.
2. `php -v` — сверить с требованием `>=8.1.0`.
3. `cd <DEPLOY_PATH> && git log -1 --format='%H %ci'` — зафиксировать,
   на каком коммите сейчас живёт прод (это и есть точка возможного отката).
4. `php yii migrate/history` (или прямой `SELECT * FROM migration ORDER BY apply_time`)
   — какие миграции прод уже считает применёнными. **Не запускать `migrate up`,
   пока не сверили этот список** — если он расходится с ожиданием
   (например, кто-то накатывал миграции вручную), сначала разобраться,
   не гадать.
5. Бэкап БД: `mysqldump` полной базы (не только `user`/`customer` — в
   отличие от точечного бэкапа для CMP-401, здесь меняется схема
   полностью, нужен full dump с возможностью restore).
6. Бэкап файлов (текущий код + `.env`) — `tar` в отдельную директорию
   вне репозитория, не поверх рабочей копии.

### 2.2. Сама выкатка

7. `git fetch && git log HEAD..origin/main --oneline` — финальная сверка
   диффа перед `pull`.
8. `git pull origin main`.
9. `composer install --no-dev --optimize-autoloader`.
10. `npm ci && npm run build` (если `build`-job CMP-40Y к этому моменту
    уже зелёный локально — сверить, что тот же результат воспроизводится
    и на сервере).
11. `php yii migrate --interactive=0` — теперь можно, после шага 2.1.4.
    Если упадёт на середине — **не паниковать и не откатывать вручную**:
    Yii2 миграции внутри одного файла идут в транзакции (`safeUp`), но
    между файлами — нет. Смотреть, какая миграция упала, сверять с
    списком «no rollback» выше, при необходимости — restore из бэкапа
    шага 2.1.5 целиком (частичный откат риskovanнее полного restore).
12. `php yii cache/flush-all`.
13. Перезапуск PHP-FPM/OPcache — способ зависит от того, что реально
    доступно на shared-хостинге (через cPanel или `touch` на
    `.htaccess`/passenger restart-файл — уточнить на месте, не
    предполагать systemctl, как ошибочно указано в
    `scripts/deploy-production.sh`, см. примечание ниже).

### 2.3. Сброс сессий (если решено ротировать ключи в это же окно)

Если в это же окно утверждена ротация `COOKIE_VALIDATION_KEY`/`auth_key`
по CMP-401 — выполнять **после** шага 12, по отдельному runbook'у
[cmp-401-cookie-rotation-runbook.md](../security/cmp-401-cookie-rotation-runbook.md).
Она разлогинивает сотрудников админки, но НЕ покупателей (разные
механизмы авторизации) — если нужно разлогинить и покупателей, это
отдельное явное решение, не побочный эффект.

## 3. Smoke-checks после выкатки

Минимум, по порядку:

1. `curl -sI https://sneaker-head.by/` → `200`.
2. `curl -sI https://sneaker-head.by/catalog` → `200` (сейчас `500` —
   это главный сигнал успеха: `518b834` действительно доехал и БД в
   рабочем состоянии).
3. Повторный запрос `/catalog` → заголовок `X-Cache: HIT` (проверяет,
   что micro-cache реально работает на этом хостинге, а не просто
   присутствует в конфиге).
4. Залогиниться в админку тестовым/боевым аккаунтом, открыть один
   существующий заказ — проверяет, что `order`/`order_history`/
   `order_item` пережили миграции без потери данных.
5. Оформить один тестовый заказ на витрине до шага оплаты (не
   подтверждать реальную оплату) — проверяет `OrderShippingService`
   (CMP-392) и checkout end-to-end.
6. `php yii queue/info` или эквивалент, если в проекте есть очереди —
   проверить, что воркеры подхватили новый код (иначе будут молча
   работать на старой версии до перezапуска).

Если шаг 2 (`/catalog` → 200) не проходит — это блокирующий фейл,
переходить к откату (раздел 4), не разбираться на живую.

## 4. План отката

Приоритет: **скорость возврата в рабочее состояние**, не сохранение
данных, накопленных за минуты простоя (их и не будет — сайт был в 500
до деплоя).

**Подтверждено симуляцией CMP-412:** точечный `migrate down` — не
альтернатива full restore, а не просто нерекомендуемый вариант. На чистой
БД `migrate down` от HEAD останавливается через 63 из 158 миграций
(`m260412_170000_fix_sidebar_menu_table` осознанно необратима). Ниже
`п.2` этого раздела всегда читать как единственный реальный путь.

1. Код: `git checkout <SHA из шага 2.1.3>` (или restore файлового бэкапа
   шага 2.1.6) → `composer install --no-dev` под старым `composer.lock`.
2. БД: если миграции гарантированно не менялись между бэкапом и
   откатом — можно попробовать точечный `migrate down` для миграций,
   применённых в этом окне (сверить со списком «no rollback» — если
   среди применённых есть хоть одна оттуда, **не пытаться `migrate down`
   частично**, сразу full restore).
3. Full restore БД из дампа шага 2.1.5 — безопасный дефолт, если
   пункт 2 не гарантирован.
4. Сброс OPcache/кэша, перезапуск PHP-FPM тем же способом, что в шаге 2.2.13.
5. Повторить smoke-checks раздела 3 против откаченной версии.
6. Сообщить совету и в этот issue результат — откат тоже требует
   комментария с причиной.

## Примечание про существующие доки

`docs/PRODUCTION_DEPLOYMENT_GUIDE.md` и `scripts/deploy-production.sh`
описывают инфраструктуру, которой, по всей видимости, не существует на
реальном таргете (Docker Compose с Elasticsearch/Redis, `systemctl
php8.1-fpm`, путь `/var/www/sneakerhead` вместо `/var/www/sneaker-head`
из `ci.yml`, пользователь `www-data`). Это похоже на аспирационный
черновик под гипотетический VPS, а не под реальный shared-хостинг
`<PROD_HOST>`. Этот runbook его не использует и не предполагает —
считать `docs/PRODUCTION_DEPLOYMENT_GUIDE.md`/`scripts/deploy-production.sh`
устаревшими до отдельной проверки на месте.
