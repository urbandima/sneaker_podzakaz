# Окно обслуживания: ротация COOKIE_VALIDATION_KEY + auth_key

Готовится по [CMP-401](../../CMP/issues/CMP-401), запускается только после явного
решения совета по [CMP-352](../../CMP/issues/CMP-352) п.6. До этого решения — не
выполнять ни один из шагов ниже на проде.

## Что и почему одним окном

- Смена `COOKIE_VALIDATION_KEY` инвалидирует все cookie, подписанные Yii2
  cookie-валидацией текущим ключом: identity-cookie `_identity-admin`
  (сотрудники админки) и CSRF-cookie. Это не влияет на уже открытые PHP-сессии
  покупателей (`session['customer_id']`) — витрина авторизует покупателей через
  сессию, а не через identity-cookie.
- Перегенерация `auth_key` обесценивает сам ключ, который лежал в утёкших
  логах, независимо от того, поменяли ли `COOKIE_VALIDATION_KEY`. Без неё
  утёкшая пара `authKey` + старый `COOKIE_VALIDATION_KEY` (если бы кто-то успел
  их сопоставить до ротации) оставалась бы валидной для подделки
  `_identity-admin` cookie сотрудника.
- Делать оба действия отдельными окнами не даёт дополнительной защиты и
  удваивает риск рассинхронизации — поэтому одно окно.

## Порядок действий

1. **Бэкап.** Снять дамп таблиц `user` и `customer` (или полный дамп БД) прямо
   перед началом окна.
2. **Dry-run на проде** (только чтение, ничего не меняет):
   ```
   php yii rotate-auth-keys
   ```
   Сверить напечатанное число строк с ожидаемым количеством активных
   покупателей/сотрудников.
3. **Заменить `COOKIE_VALIDATION_KEY`** в `.env` на новое случайное значение
   (например, `openssl rand -hex 32`) и перезапустить PHP-FPM/worker'ы, чтобы
   новое значение подхватилось.
4. **Запустить перегенерацию `auth_key`:**
   ```
   php yii rotate-auth-keys --dry-run=0
   ```
   Команда выполняет обе таблицы в одной транзакции; при любой ошибке —
   полный откат, `auth_key` не меняется ни у одной строки.
5. **Проверить эффект на админке:** залогиниться заново под тестовым
   admin-аккаунтом, убедиться, что старая `_identity-admin` cookie (сохранённая
   до шага 3) больше не пускает в систему.
6. **Решить вопрос покупательских сессий отдельно.** Шаги 3–4 не завершают уже
   открытые сессии покупателей — если совет также решил принудительно
   разлогинить покупателей (CMP-352 п.6), это отдельное действие: очистка
   серверного session storage (сброс каталога сессий / записей в session-backend)
   выполняется отдельной командой в этом же окне, до перезапуска воркеров на
   шаге 3.

## Откат

- `COOKIE_VALIDATION_KEY` — вернуть значение из бэкапа `.env`, перезапустить
  PHP-FPM/worker'ы.
- `auth_key` — восстановление возможно только из бэкапа БД (шаг 1); откатить
  сам факт ротации без бэкапа нельзя, так как новые значения не сохраняются
  нигде, кроме БД.
